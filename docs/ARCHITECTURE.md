# 软件架构与 Python 实现方案

日期：2026-10-03。本文描述准备实现的架构，不代表模块已完成。当前目录有 uv 环境和依赖配置，没有生成、评估或导出业务代码。已有角色与小修实验位于上级 `model_v2` 工程；历史脚本不是本软件的通用实现。

## 1. 首版要完成的用户流程

用户创建一个角色任务，上传或确认整体设计，确认多视图及头、身体与服装、头发的分件参考。软件生成几何候选，检查并选择，再只给选中且通过的几何生成材质。最后返回预览、资产包和可编辑 Blender 工程，用户可用自己的 Codex 继续局部精修。

默认每个零件二选一，可配置三选一。这个数量是逻辑候选数量，不假定供应商一次调用一定返回多个候选。供应商实际支持范围和计费方式在接入阶段验证。

首版先实现单角色、有限重试、单机执行。整体设计可以由用户直接提供；第一条开发链路从一张已有分件参考开始，避免同时调试所有上游步骤。

完成标准：三个零件的来源可追踪，选中几何与材质关联正确，资源能完整下载，交付工程在独立 Blender 环境可重开；未解决问题明确列出。自动精细装配、骨架绑定、动画和内部 Computer Use 不属于首版完成条件。

## 2. 总体结构

```text
用户界面 / 首轮命令行入口
            │
            ▼
Python 应用服务 ─── 任务数据库 + 本地资源目录
            │
            ▼
流程编排器（计划用 LangGraph 表达阶段和分支）
    │          │               │             │
    ▼          ▼               ▼             ▼
参考图服务   几何/材质服务    质量检查服务    交付服务
    │          │               │             │
供应商适配器 供应商适配器   网格报告 + 视图   Blender 执行器
                               │             │
                               ▼             ▼
                         Agent 决策模块    .blend + 资源包
                               │
                         接受 / 重做参考 /
                         重做几何 / 人工复核
```

Python 后端是一个应用，按模块分层。首版不拆微服务、不引入多个 Agent，也不要求分布式队列。网页界面后接，先用命令行和文件验证业务链路。

## 3. 程序、流程编排与 Agent 的职责

| 层 | 职责 | 不应承担的工作 |
| --- | --- | --- |
| 普通 Python 程序 | 提交任务、查询、下载、校验文件、预算记录、调用 Blender、保存状态 | 凭任务“成功”字段断言质量通过 |
| 流程编排器 | 按状态推进阶段、等待用户、执行有上限的重试和恢复 | 把聊天历史当作唯一状态 |
| Agent 决策模块 | 根据参考、几何检查和画面选候选，解释缺陷，建议下一步 | 任意操作文件系统或直接提交无限付费请求 |
| 用户 | 确认设计、复核不确定候选、接受交付 | 被要求手工搬运系统已经掌握的数据 |
| 用户自己的 Codex | 用户授权后的 Blender 装配和局部修复 | 被默认视为软件可直接调用的后台服务 |

即使安装了 LangChain/LangGraph，也不要求每个模块都使用框架。供应商请求、文件和 Blender 执行器保持普通 Python 接口。Agent 先以一个结构化评估函数接入；只有需要多轮工具选择时才扩展其内部行为。

## 5. 核心数据模型

| 类型 | 最低字段 | 作用 |
| --- | --- | --- |
| CharacterJob | job_id、阶段、输入参考、零件、预算、累计费用、失败原因、创建/更新时间 | 单个角色的完整任务 |
| ReferenceAsset | reference_id、类型、所属零件、文件哈希、版本、确认状态 | 固定每次生成所用参考 |
| Part | part_id、类别、候选 ID、选中候选 ID、当前阶段 | 管理头/身体/头发，避免靠文件名关联 |
| GeometryCandidate | candidate_id、reference_id、供应商与任务 ID、版本、状态、资产 ID | 区分逻辑候选和供应商任务 |
| QualityReport | candidate_id、输入哈希、检查视图、网格报告、缺陷、硬门槛、评估配置 | 让质量结论可复核 |
| Decision | part_id、候选、路由、理由、证据 ID、人工复核需求、来源 | 决定下一步，来源区分人工与模型 |
| TextureResult | candidate_id、几何版本、供应商任务 ID、输出资源、检查状态 | 材质严格绑定选中几何 |
| Artifact | artifact_id、用途、相对路径、哈希、格式、创建来源 | 管理参考、模型、贴图、预览与报告 |
| CostEvent | 操作 ID、供应商任务 ID、预估/实际、金额或积分、币种、状态 | 失败与重试也进入账本 |
| JobEvent | job_id、操作 ID、阶段变化、时间、结果或错误 | 排查中断与恢复 |

状态保存在数据库，文件保存在任务目录。引用文件通过 Artifact ID 解析，不把机器绝对路径写成跨机器身份。API 密钥留在配置层，不进入任务导出、日志或 Agent 提示词。

供应商 task_id、job_id 和 candidate_id 是三种身份。一个任务返回多个产物时，要分别登记候选，不能因它们共享 task_id 而覆盖彼此。

## 6. 工作流与失败处理

角色级阶段：

```text
created → preparing_references → awaiting_reference_review
        → generating_geometry → reviewing_geometry
        → generating_textures → reviewing_textures
        → exporting → awaiting_delivery_review → completed
```

等待人工、失败、取消和预算不足单独记录。零件有各自状态，不能因为头部需要重做而让已经通过的身体和头发重复生成。

几何检查允许四种决定：`accept`、`regenerate`、`fix_reference`、`human_review`。严重结构问题不能仅凭外观评分高而自动通过；不确定时进入人工复核。材质失败另外路由到材质重试或交接小修，只有发现几何缺陷时才退回几何阶段。

材质提交前，程序必须验证选中候选、几何通过状态、实际资源、参考/几何版本及剩余预算。Agent 的建议经过这些条件后才能执行。更换候选或几何版本后，旧材质不能自动沿用。

每个外部操作使用稳定操作 ID，提交前保存意图，取得响应后保存供应商任务 ID。超时要区分“确认未提交”和“结果未知”；结果未知先查询。如果供应商不提供可查询关联或幂等能力，转人工核对，不能盲目重发付费任务。

首版每个任务由一个执行者推进，SQLite 事务管理状态。允许取消后，阻止后续新提交；已开始的供应商任务未必能取消，应查询并记入实际费用。进程重启时从数据库恢复，而不是重新生成全部资源。

## 7. 质量评估接口

建议的业务接口（并非某个 SDK 的真实方法名）：

```python
async def evaluate_candidates(
    part: Part,
    candidates: list[GeometryCandidate],
    reports: list[QualityReport],
    references: list[ReferenceAsset],
) -> Decision:
    ...
```

先由确定性工具检查文件和网格、输出固定多视图与必要线框，再把报告和图像交给评估模型。模型返回结构化决定，由 Pydantic 校验字段、候选身份及证据引用。枚举合法不等于质量判断正确，还需人工基线实验。

多角度截图不能单独证明拓扑良好。眼窝凹陷需要几何信息；眼周圆形边流需要线框/拓扑信息和明确用途要求。开放头发片、衣服边界不能全部当作错误孔洞。

第一版只做一次评估加有限重试。记录模型、提示词版本、原始结果、实际用量和人工判断，后续再比较二选一与三选一的成本收益。

## 8. Blender 执行与交付

用户无需预先安装 Blender 就能提交生成任务。生成 `.blend` 的工作机或服务器需要可用 Blender；Python 项目通过受控子进程运行检查与导出脚本，不能假设 `uv add` 一个包就能替代完整 Blender 环境。

首版固定 Blender 版本和预览条件。每个任务使用独立目录与新场景，不操作开发者或用户正在编辑的工程。执行器设置超时，收集退出码、日志和产物；脚本成功退出后仍需检查结果文件。

交付先做到：导入三类零件、统一登记单位与变换、建立可编辑对象、配置材质和检查视图、打包可嵌入资源。自动对齐是否达到完整角色效果需要单独验证；只把零件放进场景时，交付状态必须写“待装配”，不能标成成品角色。

交付包规划：

```text
character-delivery/
  character.blend
  manifest.json
  CODEX_HANDOFF.md
  references/
  previews/
  assets/                   # 必要的外部资源及原始生成资产
  reports/
```

在与生成环境隔离的资源目录中重开工程，检查贴图、外部依赖及对象完整性后再标记交付。无法嵌入的资源随包附带并使用相对路径；插件依赖明确声明。

## 9. Python 依赖选择

当前已配置：`httpx`、`pydantic`、`python-dotenv`、`langchain`、`langgraph`，开发工具为 `pytest`、`ruff`。

- HTTP 请求与查询使用 httpx；数据结构和模型返回值校验使用 Pydantic。
- LangGraph 用于阶段和决策分支；数据库负责长期状态，不能依赖仅存内存的流程状态。
- LangChain 可用于确有需要的模型适配，不与供应商 HTTP 层强耦合。
- 初期 SQLite 和文件系统可以用 Python 标准库实现。
- FastAPI、供应商/模型 SDK，以及网格处理依赖，在实现相应接口时再添加。

不在首版引入 Redis、Celery、多 Agent、向量数据库或分布式集群。任务规模增长、并发与部署需求明确后再评估。

## 10. 开发顺序

1. **数据与记录**：定义任务、候选、决策、材质、产物和费用模型；写存取和状态变更。
2. **单零件真实链路**：已有参考 → 一个几何候选 → 人工检查 → 单独材质生成 → 下载。核实接口关联、几何变化和真实计费。
3. **检查与二选一**：固定视图、网格报告、结构化 Agent 决策、有限重试；比较人工基线。
4. **三零件与交付**：独立零件状态、资源清单、Blender 导出和隔离重开验证。
5. **完整设计入口与网页**：整体/多视图/分件参考确认，任务进度、预览和下载。
6. **小批量实验**：5 个角色、15 个零件选择任务，二选一对应初轮 30 个几何候选，统计全部失败支出与人工时间。

优先测试会影响费用和交付的约束：未通过几何不提交材质、换候选使旧材质失效、未知提交结果不重复下单、部分失败不重做通过零件、资源缺失不标交付完成。供应商集成测试与付费试验分开，付费试验使用明确预算。

## 11. 可行性证据与成本边界

本地小修实验约 6–7 分钟，处理背部材质混色和单处头发裂口，没有额外图片或 3D 生成调用。它支持保留“用户自己的 Codex 精修”作为交接路线；不能证明软件内自动评估、批量生成或通用装配已完成。

每角色约 3.5 美元仍是讨论预算，不能写成平均实测价。记录参考生成、全部几何候选、材质、评估、执行和失败重试支出；用户订阅费用和人工时间分别列出。准确结论以真实任务账单与合格交付数量为准。

## 12. OpenAI 官方 Agent 工具核查与选型

核查日期：2026-10-03。

[Agent Builder](https://developers.openai.com/api/docs/guides/agent-builder) 提供可视化节点、模板、预览和工作流代码导出，能够加快 Agent 原型搭建。但[官方弃用公告](https://developers.openai.com/api/docs/deprecations)记录其计划于 2026-11-30 关闭，不建议作为本项目新开发的长期运行依赖。

[OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk) 支持在自己的 Python 应用中运行 Agent，由 SDK 处理 Agent 循环及工具调用，应用负责工具实现、状态、部署和审批逻辑。这是值得对比的代码实现路线，不会自动提供 Tripo、Blender 或当前桌面 Codex 的全部能力。

本项目当前建议：

- 生成适配器、网格/视图检查、预算控制、数据库及 Blender 执行器保留普通 Python 模块。
- 对候选评估，先明确输入报告和结构化 Decision，再选择普通模型调用或 Agents SDK；简单一次性判断未必需要完整 Agent 循环。
- 如果 Agent 要主动要求额外视图或调用检查工具，Agents SDK 可作为评估模块的运行层候选。
- LangGraph 当前仅为已安装的流程编排候选；不是已经确定必须使用。避免为了框架重复维护两套任务状态或两层 Agent 循环。
- 用一个“读取候选报告 → 必要时请求额外检查 → 输出选择及理由”的小实验比较实现难度，再确定框架。未安装或调用 OpenAI SDK，未新增付费请求。

以上是本项目的架构判断；产品事实依据官方链接。账号是否能进入 Agent Builder、实际模型权限及费用没有在登录账号内验证。
